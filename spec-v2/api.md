# API и безопасность

## 1. Общие требования

- API использует REST и JSON.
- Все endpoints MVP находятся под `/api/v1`.
- Публичные идентификаторы ресурсов имеют формат UUIDv7.
- Актуальная OpenAPI-спецификация является обязательной частью проекта.
- Frontend-типы генерируются из OpenAPI либо проверяются на соответствие ей в CI.
- API не возвращает локализованный пользовательский текст там, где достаточно машинного кода.
- Все пользовательские тексты при выводе экранируются.

Минимальные группы endpoints:

- регистрация, вход, refresh, logout и получение текущего пользователя;
- чтение и изменение профиля;
- загрузка, просмотр и удаление медиа;
- получение публичных счётчиков;
- список, создание, переименование, удаление и snapshot деревьев;
- чтение, создание, изменение и удаление персон;
- создание и удаление родительских связей;
- создание, изменение и удаление периодов брака;
- чтение, создание, изменение, упорядочивание и удаление событий.

OpenAPI детализирует поля request/response, но не должна менять назначение и базовые пути следующей карты.

### 1.1 Карта endpoints

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/v1/statistics` | Текущие публичные счётчики аккаунтов и деревьев |
| `POST /api/v1/auth/register` | Регистрация и создание первой сессии |
| `POST /api/v1/auth/login` | Вход по логину или email |
| `POST /api/v1/auth/refresh` | Ротация refresh-токена и выдача access-токена |
| `POST /api/v1/auth/logout` | Отзыв текущей сессии |
| `GET /api/v1/me` | Текущий пользователь и его профиль |
| `PATCH /api/v1/me` | Изменение языка профиля |
| `POST /api/v1/me/avatar` | Загрузка и crop аватара |
| `DELETE /api/v1/me/avatar` | Удаление аватара |
| `GET /api/v1/trees` | Список деревьев владельца |
| `POST /api/v1/trees` | Создание пустого дерева |
| `PATCH /api/v1/trees/{treeId}` | Переименование дерева |
| `DELETE /api/v1/trees/{treeId}` | Удаление дерева |
| `GET /api/v1/trees/{treeId}/snapshot` | Компактный snapshot графа и ETag |
| `PUT /api/v1/trees/{treeId}/reference` | Назначение опорной персоны или существующего брака |
| `POST /api/v1/trees/{treeId}/graph-mutations` | Одна атомарная структурная команда |
| `GET /api/v1/trees/{treeId}/people/{personId}` | Полные данные выбранной персоны |
| `PATCH /api/v1/trees/{treeId}/people/{personId}` | Автосохранение одного или нескольких согласованных полей |
| `POST /api/v1/trees/{treeId}/people/{personId}/photo` | Загрузка полной фотографии и crop `3:4` |
| `GET /api/v1/trees/{treeId}/people/{personId}/photo` | Защищённая выдача полной фотографии |
| `DELETE /api/v1/trees/{treeId}/people/{personId}/photo` | Удаление основной фотографии |
| `GET /api/v1/trees/{treeId}/people/{personId}/events` | Timeline выбранной персоны |
| `POST /api/v1/trees/{treeId}/people/{personId}/events` | Создание ручного события |
| `PATCH /api/v1/trees/{treeId}/people/{personId}/events/{eventId}` | Изменение ручного события |
| `DELETE /api/v1/trees/{treeId}/people/{personId}/events/{eventId}` | Удаление ручного события |
| `PUT /api/v1/trees/{treeId}/people/{personId}/event-order` | Порядок событий в неоднозначных группах |
| `PATCH /api/v1/trees/{treeId}/marriages/{marriageId}` | Изменение дат существующего периода брака |

`graph-mutations` принимает ровно одну дискриминированную команду:

- `create_first_person`;
- `add_parent`;
- `add_child`;
- `link_parent_child`;
- `add_marriage_period`;
- `remove_parent_link`;
- `remove_marriage_period`;
- `delete_person`.

Команды добавления принимают либо ID существующей персоны, либо вложенные данные новой персоны, но не оба варианта одновременно. `add_child` атомарно создаёт одну персону и одну или две родительские связи. Каждая команда передаёт полный набор изменяемых координат.

Изменение дат брака через `PATCH` синхронизирует автоматические события. Если изменение требует перестроения графа, оно выполняется через `graph-mutations`.

### 1.2 Базовые HTTP-коды

- `200 OK` — успешное чтение или изменение с телом ответа;
- `201 Created` — создан новый ресурс;
- `204 No Content` — успешное удаление без тела;
- `400 Bad Request` — неразбираемый JSON или нарушение формы wire-типа;
- `401 Unauthorized` — отсутствующая или недействительная сессия;
- `404 Not Found` — отсутствующий либо недоступный владельцу приватный ресурс;
- `409 Conflict` — уникальность или доменный конфликт, не связанный с версией snapshot;
- `412 Precondition Failed` — несовпадение `If-Match`;
- `413 Content Too Large` — превышение допустимого размера загрузки;
- `415 Unsupported Media Type` — неподдерживаемый тип тела или изображения;
- `422 Unprocessable Content` — ошибки полей и доменной валидации;
- `500 Internal Server Error` — непредвиденная серверная ошибка без раскрытия деталей.

## 2. Авторизация

### Access-токен

- Срок жизни — 15 минут.
- Передаётся как Bearer token.
- Frontend хранит его только в памяти.
- Токен связан с серверной сессией.
- Каждый защищённый запрос проверяет, что сессия существует и не отозвана.

### Refresh-токен

- Максимальный срок жизни — 30 дней.
- Хранится в `HttpOnly`, `Secure`, `SameSite` cookie.
- Cookie ограничивается API-путём, необходимым для refresh/logout.
- Токен ротируется при каждом успешном refresh.
- Повторное использование уже заменённого refresh-токена отзывает соответствующую сессию.
- Refresh-токен не возвращается JavaScript-коду frontend.

### Сессии

- Каждый вход с нового устройства или браузерного профиля создаёт независимую сессию.
- Обычный logout отзывает только текущую сессию.
- После logout связанный access-токен немедленно перестаёт работать.
- Управление списком сессий и «выйти на всех устройствах» не входят в MVP.

### Локальный HTTPS

Docker Compose должен поднимать HTTPS reverse proxy для `localhost`. Инструкция запуска описывает создание или подключение dev-сертификата и добавление его в доверенные на машине разработчика.

Режим работы refresh-cookie без флага `Secure` не является штатным режимом MVP.

## 3. Права доступа

- Каждый endpoint дерева и вложенных ресурсов проверяет владельца.
- Нельзя получить чужое дерево подбором UUID.
- Чужой или несуществующий приватный ресурс возвращает одинаковый результат, не раскрывающий его существование.
- Проверка выполняется backend, независимо от скрытия элементов frontend.
- Полные изображения и производные файлы выдаются только после такой же проверки владельца.
- Постоянные публичные URL изображений запрещены.

## 4. Ошибки

Все ошибки имеют единый JSON-формат:

```json
{
  "code": "TREE_VERSION_CONFLICT",
  "message": "tree_version_conflict",
  "fields": {
    "name": ["tree_name_not_unique"]
  },
  "details": {}
}
```

Правила:

- `code` — стабильный машинный код ошибки;
- `message` — необязательный машинный ключ общего сообщения;
- `fields` — ошибки конкретных полей;
- `details` — только безопасные структурированные данные;
- локализованный текст формирует frontend;
- ошибки авторизации не раскрывают, существует ли логин или email;
- технические исключения, SQL, stack trace, токены и пути файлов не возвращаются клиенту.

## 5. Wire-типы

### Известный или неизвестный текст

```json
{ "state": "known", "value": "Иван" }
```

или:

```json
{ "state": "unknown" }
```

Пустая строка не заменяет состояние `unknown`.

### Пол

```json
"male"
```

Допустимые значения: `male`, `female`, `unknown`.

### Структурированная дата

Неизвестная дата:

```json
{ "state": "unknown" }
```

Известная дата:

```json
{
  "state": "known",
  "kind": "exact",
  "year": 1994,
  "month": 10,
  "day": 25
}
```

`kind` принимает `exact`, `approximate`, `before`, `after` или `between`.
Для `between` обязательно добавляется объект `end` с `year`, необязательными
`month` и `day`. Для остальных видов `end` отсутствует.

Поля, у которых отсутствие имеет самостоятельный смысл, дополнительно допускают `null`. Например:

- `deathDate: null` — персона жива;
- `dissolutionDate: null` — брак действует.

### Координаты

```json
{
  "x": 1200.5,
  "y": -340.0
}
```

Обе координаты обязательны и должны быть конечными числами. `NaN`, бесконечность и отсутствующие компоненты отклоняются.

### Родительская связь

```json
{
  "id": "019...",
  "parentId": "019...",
  "childId": "019...",
  "role": "father"
}
```

Допустимые роли: `father`, `mother`.

### Период брака

```json
{
  "id": "019...",
  "malePersonId": "019...",
  "femalePersonId": "019...",
  "marriageDate": { "state": "unknown" },
  "dissolutionDate": null
}
```

### Событие

Событие передаёт:

- ID персоны;
- тип;
- источник `automatic` или `manual`;
- структурированную дату;
- название и описание, если применимы;
- типизированные данные события;
- ID сущности-источника для автоматического события;
- позицию ручного порядка внутри неоднозначной группы.

Поля, недоступные для конкретного типа события, не должны приниматься «на будущее».

## 6. Snapshot дерева

При открытии редактора одним запросом загружается компактный snapshot:

- метаданные дерева;
- текущий ETag;
- nullable-опору вида `{ "type": "person", "personId": "..." }` или `{ "type": "marriage", "personIds": ["...", "..."] }`;
- данные, необходимые для каждой карточки;
- ID основной производной фотографии либо защищённый endpoint миниатюры;
- родительские связи;
- периоды браков в объёме, необходимом для построения линий;
- ID и время изменения ресурсов.

Полные данные выбранной персоны, timeline событий и полное изображение загружаются отдельными запросами.

API не требует загружать весь оригинал фотографии или полные описания всех событий для первого рендера графа.

`PUT /api/v1/trees/{treeId}/reference` требует актуальный `If-Match` и принимает ровно один discriminated union:

```json
{ "type": "person", "personId": "019..." }
```

```json
{ "type": "marriage", "personIds": ["019...", "019..."] }
```

Backend проверяет принадлежность персон дереву, их различие и существование хотя бы одного периода брака пары. Пара хранится в каноническом порядке UUID независимо от порядка запроса и конкретного периода брака.

## 7. Конкурентное редактирование

Ответ snapshot содержит HTTP `ETag`, представляющий текущую версию всего изменяемого состояния дерева.

Каждая мутация дерева или вложенного ресурса:

- передаёт полученное значение в `If-Match`;
- выполняется только при совпадении версии;
- возвращает новый ETag после успеха;
- отклоняется при несовпадении с HTTP `412 Precondition Failed` и кодом `TREE_VERSION_CONFLICT`.

В версию входят:

- данные дерева;
- персоны;
- связи;
- периоды браков;
- события;
- опора дерева и состояние силовой карты;
- ссылки на основные медиа.

Viewport браузера в версию не входит.

Frontend при конфликте:

1. прекращает последующие автосохранения;
2. показывает локальное неподтверждённое значение;
3. сообщает о параллельном изменении;
4. предлагает загрузить актуальный snapshot;
5. не пытается автоматически повторять или сливать операцию.

## 8. Структурные мутации

К структурным относятся:

- добавление новой персоны через связь;
- связывание существующих персон;
- удаление персоны или связи;
- создание или удаление периода брака.

Backend в одной транзакции:

1. проверяет владельца и `If-Match`;
2. проверяет все доменные инварианты;
3. проверяет принадлежность ID дереву;
4. применяет изменение графа и при необходимости заменяет разрушенную опору;
5. синхронизирует автоматические события;
6. фиксирует новую версию дерева;
7. возвращает новый ETag и изменённые данные.

Частичный успех запрещён.

## 9. Медиа API

Загрузка изображения должна:

- принимать JPEG, PNG или WebP;
- ограничивать исходный файл 10 МБ;
- ограничивать декодированное изображение 20 мегапикселями;
- определять формат фактическим декодированием, а не расширением;
- отклонять SVG и анимированные изображения;
- удалять EXIF и другие метаданные;
- создавать требуемые производные;
- записывать файл через Flysystem.

Удаление или замена вложения должны согласованно изменять БД и физические файлы. Неиспользуемый файл не должен оставаться доступным через API.

## 10. Не входящие в MVP механизмы безопасности

В MVP отсутствуют:

- rate limiting регистрации, входа и refresh;
- аудит попыток аутентификации;
- подтверждение email;
- восстановление пароля;
- смена логина, email и пароля;
- удаление аккаунта;
- CAPTCHA.

Это допустимо только потому, что MVP является локальным прототипом. Эти исключения перечисляются также в [quality.md](quality.md).
